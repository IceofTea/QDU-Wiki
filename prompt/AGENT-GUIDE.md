## 一、项目目的

**青岛大学 Wiki（QDU-Wiki）** 是一份**非官方**的校园生存指南，由百度贴吧【青岛大学吧】的吧友与热心校友共同维护。

- **服务对象**：青岛大学新生（主要）与老生
- **核心价值**：帮新生完成从「拿到录取通知书」到「融入校园生活」的全流程过渡——报到准备、校区选择、军训、选课、考试、宿舍、餐饮、社团、组织关系等
- **内容风格**：说人话、讲干货、接地气。允许轻松幽默（~~删除线吐槽~~、emoji），但要确保信息准确、对新生有用
- **重要定位**：是「新生手册」性质的内容站，不是学校官网的复刻。所有内容都应体现「过来人的经验与信息差」

> **对 Agent 的第一条要求**：所有修改都必须服务于「帮助新生/老生更好地了解青大」这一目的。不要为了形式而堆砌内容，也不要写官腔。

## 二、项目架构

### 2.1 技术栈

| 项目 | 说明 |
| --- | --- |
| 静态站点生成器 | **MkDocs** + **Material** 主题 |
| 内容形式 | 纯 Markdown（`docs/` 下所有 `.md` 文件） |
| 导航 | `mkdocs.yml` 中的 `nav:` 字段 |
| 样式 | `docs/stylesheets/extra.css`（自定义） |
| 交互 | `docs/javascripts/home-hero.js`、`docs/javascripts/season-switcher.js` |
| 部署 | GitHub Actions（`.github/workflows/ci.yml`）自动构建并部署到 GitHub Pages |
| 数据存储 | 内容全部内嵌在 Markdown 中；大文件（资料 PDF、图片等）走外部网盘链接 |

### 2.3 核心配置文件 `mkdocs.yml`

- `nav:` 定义了全站导航结构。**新增或移动页面后必须同步修改 nav**，否则新页面无法访问
- `theme:` 使用 Material，开启了 `navigation.tabs`、`navigation.instant`、`navigation.indexes` 等
- `markdown_extensions:` 启用了 `admonition`、`pymdownx.tabbed`、`pymdownx.details`、`attr_list`、`md_in_html`、`pymdownx.superfences` 等，意味着这些语法在站内可用
- `plugins:` 使用 `search` + 两个 git 插件（CI 环境外默认关闭）
- `extra_css` / `extra_javascript` 引用了自定义样式与脚本

> **对 Agent 的要求**：修改 `mkdocs.yml` 时务必保持 YAML 缩进正确（每级 2 空格），不要删除或重排已有导航项，只做「追加」或「在明确要求下的局部调整」。

## 三、页面逻辑与内容惯例

### 3.1 导航与板块

全站 9 大板块（导航顶层）：
1. 主页
2. 新生手册 `new/`
3. 生活指南 `live/`
4. 学习学业 `study/`
5. 校园服务 `service/`
6. 学院详情 `college/`
7. 学生组织 `organization/`
8. 文件共享 `share/`
9. 有话送你 `words/`
10. 关于 Wiki `about/`

### 3.2 常见页面结构

- **正文以 `# 页面标题` 开头**（H1），小节用 `##`、`###`
- 善用 Material 的提示框语法（详见下节）
- 需要「待补充」的地方，用 `!!! warning "待更新"` 或 `!!! info` 标注，方便后续维护者搜索定位
- 内容性信息尽量用**表格**呈现（对比、清单、联系方式等），可读性高
- 涉及政策/规则类的页面，通常在开头用 `!!! tip "文件依据"` 注明出处文件与文号（如「青大教字〔2021〕21号」），并加一句「如有变动以官方最新文件为准」

### 3.3 提示框（Admonition）用法

| 类型 | 语法 | 用途 |
| --- | --- | --- |
| 注意 | `!!! note "标题"` | 一般性说明 |
| 提示 | `!!! tip "标题"` | 过来人经验、小技巧 |
| 警告 | `!!! warning "标题"` | 重要提醒 |
| 危险 | `!!! danger "标题"` | 严重警示（如作弊、诈骗） |
| 引用 | `!!! quote "标题"` | 引言、备注、署名 |
| 成功 | `!!! success "标题"` | 已完成 / 好消息 |

用法示例：

```markdown
!!! tip "省钱技巧"
    家乡离青岛较远的同学能省不少钱，记得利用好这次优惠。
```

### 3.4 链接与图片路径

- **相对路径**：站内互相引用一律用相对路径。`docs/new/x.md` 引用同目录文件写 `y.md`；引用 `docs/college/` 下文件写 `../college/y.md`
- **图片**：统一放 `docs/pics/` 下对应板块子目录（`pics/new/`、`pics/live/` 等），引用路径随页面所在目录变化（根目录页面 `docs/index.md` 用 `pics/xxx.png`，子目录页面用 `../pics/xxx.png`）
- **命名**：`<板块>-图<编号>-<描述>.png`，如 `study-图1-校历.png`
- **外部链接**：直接写完整 URL

### 3.5 中英文排版

中英文之间、中文与数字之间加一个空格（如「使用 MkDocs 构建」「2026 级新生」），读起来更舒服。这与仓库已有页面保持一致。

### 3.6 学院详情页 `college/`

- `index.md` 是学院索引页，按「医学类 / 理工类 / 人文社科类 / 经管类 / 艺术类 / 继续教育类」分组，表格列出各学院、简介、状态、详情链接
- 每个学院一个独立 `.md`，文件名用英文（如 `computer_science_and_technology.md`、`school_of_medicine.md`）
- 模板结构：学院简介 → 专业设置 → 特色培养 → 校区安排 → 学习与竞赛建议 → 保研与就业 → 常见问题 → 贡献
- 未维护的学院页保持模板占位（`待更新`），已维护的（如计算机科学技术学院）内容充实

> **对 Agent 的要求**：新增学院页面时，先看看同目录已有页面的模板结构，保持一致。

!!! warning "关于「未完成维护的学院页」"
    未完成维护的学院**不保留占位文件**：不建 `.md`、不进 `mkdocs.yml` 的 nav、不进 `college/index.md` 列表。只有内容基本完整的学院才创建文件并加入导航与索引展示（参考计算机科学技术、机电工程、化学化工三学院）。空占位页会污染站内搜索与知识库索引、影响检索质量，一律不保留。

## 四、维护方法

### 4.1 三种维护来源

本站信息主要来自三处，Agent 都要能处理：

1. **社区提交的 `prompt.md` 提示词**：社区成员按「定位 + 原文 + 修改内容 + 显示格式」的格式写入修改需求。Agent 据此定位文件、替换内容。
2. **直接上传的信息源**：图片（截图/海报）、文档（PDF/Word）、聊天记录等原始素材，需要 Agent 提炼文字、整理成结构化 Markdown。
3. **明确的修改指令**：维护者直接告诉 Agent 改哪里、怎么改。

### 4.2 信息源的处理方式

- **图片**：用 OCR（如 RapidOCR）提取文字，再整理成 Markdown 表格/列表
- **长文档**：提炼关键信息，按板块拆分补充到对应页面，避免整篇堆砌
- **口述/回忆录式文字**：整理润色后按页面结构写入

> **原则**：信息源是「原材料」，Agent 的职责是**加工成符合本站风格与结构的 Markdown 内容**，而不是原样粘贴。

### 4.3 自主采集信息源（无需人工投喂）

生活板块（餐饮/住宿/交通/医疗/设施/购物）信息容易过时，且官网首页看不到、论坛信息太脏。Agent 应能**自己联网采集新鲜信息**。以下信息源已实测可用（截至 2026-07）：

5. 草稿开头加 `!!! warning "待更新草稿"`，正文逐条标注信息来源与采集日期

## 五、Agent 维护工作流（必读）

每次维护任务，请严格按以下流程执行：

### 第 1 步：通读本文档与上下文

- 完整阅读本文档（AGENT-GUIDE.md）
- 阅读 `mkdocs.yml` 了解当前导航结构
- 阅读与任务相关板块的现有页面，理解其风格与结构

### 第 2 步：定位信息源

- 若维护指令来自 `prompt.md`，先读取其中的需求
- 若维护指令引用了图片/文档，先提取文字内容并归纳

### 第 3 步：设计改动方案

- 明确「改哪个文件 / 新增哪个文件 / 是否动导航」
- 尽量**复用现有结构与样式**，不要引入新概念或新组件（除非维护者明确要求）
- 若需新增页面，决定它在 `mkdocs.yml` 导航中的位置

### 第 4 步：执行修改

- 只改动本次任务相关的文件，**不顺手重构无关内容**
- 保持中文排版规范、表格对齐、提示框语法正确

### 第 5 步：本地验证

在项目根目录执行构建验证，确保没有错误：

```powershell
python -m mkdocs build --strict
```

- 若输出 `INFO - Documentation built in X seconds` 且无 warning/error，说明构建通过
- 有 warning 也要修复（`--strict` 会把警告当错误）
- 构建产物 `site/` 是自动生成的，**不需要也不应该手动修改或提交**

### 第 6 步：复查与提交（若被要求提交）

- 复查改动：diff 是否只包含预期修改
- 提交信息遵循 README 规范：`<类型>(<文件名>): 干了什么`，类型有 `feat`/`fix`/`refactor`/`revert`
- 提交前检查 `git status`，避免误提交临时文件或敏感信息

## 六、质量红线（避免「一次失误搞崩网站」）

以下规则是**硬性红线**，违反任一条都可能破坏网站，请务必遵守：

1. **永远先构建再交付**：任何修改后都必须执行 `python -m mkdocs build --strict`，确认通过后才算完成。
2. **改 `mkdocs.yml` 时小心缩进**：YAML 缩进错误会直接导致构建失败。新增导航项务必与同级已有项缩进一致。
3. **不要删除或重排已有导航项**：只做追加；确需调整时应最小化变更。
4. **相对路径必须正确**：站内链接用相对路径，写错会 404。改文件位置时同步改所有引用它的链接。
5. **不破坏特殊语法**：admonition、`md_in_html` 块、表格、代码块都必须闭合正确；`<div class="grid cards">` 等 HTML 块尤其要注意结构完整。
6. **不引入外部依赖**：不要新建需要额外 JS/CSS/插件的功能（除非明确要求）。现有功能的改动要尽量在不破坏现有结构的前提下完成。
7. **不改 `site/` 目录**：它是构建产物，会被 CI 覆盖。
8. **信息准确性优先**：不确定的信息不要编造；无法核实的标「待更新」。特别是官方文件（文号、时间、电话）必须与信息源一致。
9. **不提交敏感信息**：个人手机号、身份证号、家庭住址等敏感信息要脱敏或仅在必要场景保留（校园公开电话除外）。
10. **修改文档类说明时保持一致**：如果更新了页面结构/命名规则，记得同步更新本文档或相关维护说明。

### 2026-08-18（补）：首页统计数字「一闪一闪一卡一卡」根因修复

- **任务**：维护者反馈第一页「累计访问」数字仍闪烁且更严重——定位根因非打字机光标，而是统计数字的 count-up 滚动动画。
- **根因**：`visit-counter.js` 的 `animateNum()` 数字滚动动画（DURATION=1000ms）+ `start()` 每 500ms 轮询 30s：Vercount 锚点回填/更新期间，每次 `apply()` 读到新值就触发一次从低到高的数字翻滚（实测采样 `4→116→151→161→163→164`），造成「一卡一卡一闪一闪」。
- **改动**：`docs/javascripts/visit-counter.js`——删除 `animateNum()` 及 `DURATION` 常量，`fillCards()` 改为直接 `textContent = format(值)`（千分位不变，一次到位）。
- **说明**：数据链路（Vercount 注入/API 直连/sessionStorage 缓存/instant 兜底）完全不变，仅去掉动画；首次填充由占位符 `···` 一次性变为数值，视觉稳定。打字机光标已在上轮优化（平滑淡入淡出 + 删除完隐藏），本轮核实为正常柔和闪烁。构建 `python -m mkdocs build --strict` 通过；实测数字采样变化次数由 6 → 1（仅占位→数值一次跳变），无 JS 错误。
